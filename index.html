دوام چیست

یک سامانه‌ی CMMS/PMS تحت وب برای هر سازمانی که دارایی فیزیکی دارد و باید نگهش دارد. منطقش به صنعت خاصی گره نخورده — تجهیز، برنامه‌ی نگهداری، دستور کار، خرابی و شاخص در هر صنعت دارایی‌محور یکسان‌اند.

یک نکته‌ی صادقانه: نسخه‌ی فعلی واژگان صنعت حفاری را دارد — واحد تفکیک دارایی‌ها «دکل» نامیده می‌شود. برای استقرار در صنعتی دیگر این برچسب متناسب با همان صنعت («کارخانه»، «سایت»، «خط») تنظیم می‌شود؛ ساختار و منطق زیرین تغییری نمی‌کند.

🌳 شناسنامه‌ی دقیق ناوگان

تجهیزات در یک سلسله‌مراتب چندسطحی تعریف می‌شوند — از دکل تا کوچک‌ترین قطعه‌ی قابل تعویض — و هر آیتم کد فنی، مدل و سابقه‌ی خودش را دارد. ساختار موجود سازمان به‌صورت انبوه از اکسل وارد می‌شود، پس راه‌اندازی به ورود دستی هزاران رکورد نیاز ندارد.

📅 نگهداری پیشگیرانه‌ی خودکار

دوره‌های روزانه، هفتگی و ماهانه روی تقویم شمسی تعریف می‌شوند و سامانه هر شب خودش دستور کار روز بعد را می‌سازد. برنامه‌ها و چک‌لیست‌هایشان از فایل قابل ایمپورت و ویرایش‌اند.

⛔ انضباط تأخیر

کار عقب‌افتاده بدون ثبت دلیل تأخیر بسته نمی‌شود. این تنها چیزی است که نمی‌گذارد گزارش ماهانه به یک صفحه‌ی تماماً سبزِ بی‌معنا تبدیل شود — و همان قابلیتی است که مدیر واقعاً به آن تکیه می‌کند.

⚠️ مدیریت خرابی و توقف

خرابی با زمان شروع و پایان ثبت می‌شود و مدت توقف خودکار محاسبه می‌گردد. قطعات مصرفی، شرح رفع و اقدام پیشگیرانه نگه داشته می‌شوند — همان داده‌ای که بدون دخالت انسان به شاخص‌های قابلیت اطمینان تبدیل می‌شود.

📈 شاخص‌های قابلیت اطمینان

MTBF، MTTR و دسترس‌پذیری همراه با ساعت توقف و تعداد تجهیزات درگیر، قابل تفکیک بر اساس دکل، دپارتمان و بازه‌ی زمانی تا یک سال. روند ناوگان روی محدوده‌های رنگی نمایش داده می‌شود تا افت عملکرد قبل از بحرانی شدن دیده شود.

📗 خروجی اکسل حرفه‌ای

از هر فهرستی خروجی گرفته می‌شود. خروجی چک‌لیست نگهداری هر دپارتمان را در شیت جداگانه می‌چیند، وضعیت هر آیتم را علامت می‌زند و سررسید و دلیل تأخیر را هم می‌آورد — با بازه‌ی زمانی کاملاً انعطاف‌پذیر.

🧾 درخواست کالای پیشرفته با رهگیری دقیق

هر درخواست از لحظه‌ی ثبت تا تحویل کالا قابل ردیابی است و در هر لحظه معلوم است روی میز چه کسی مانده. گردش تأیید چندمرحله‌ای است و شرط مبلغی دارد: خریدهای کوچک مسیر کوتاه‌تری می‌روند.

🔎 تشخیص گلوگاه خرید

خط خرید به‌صورت مراحل پشت‌سرهم دیده می‌شود و سامانه انگشت می‌گذارد روی جایی که کار واقعاً معطل شده. مدیر لازم نیست دنبال کسی بگردد.

⚖️ کنترل تطبیقی سه‌جانبه

سفارش، رسید انبار و فاکتور با هم مقایسه می‌شوند و مغایرت خودکار علامت می‌خورد؛ تعهد باز پس از تأیید به هزینه‌ی قطعی تبدیل می‌شود.

🏬 انبار با تاریخچه‌ی کامل

موجودی چند انبار، کالای در راه و تاریخچه‌ی گردش هر قلم نگه داشته می‌شود. اقلام تعمیرپذیر و گارانتی‌دار مسیر خودشان را دارند، و مصرف قطعات مستقیم به هزینه‌ی نگهداری همان تجهیز وصل می‌شود. کنترل مالی چندارزی و تنخواه هر دکل هم پشتیبانی می‌شود.

📜 نامه‌نگاری اداری کامل

نامه با سربرگ رسمی ساخته می‌شود، شماره‌ی اتوماتیک می‌گیرد، مسیر تأییدش را طی می‌کند و با امضای اسکن‌شده مهر می‌شود. گیرنده‌ی داخلی و خارج از سازمان، رونوشت، پیوست، درجه‌ی محرمانگی و فوریت پشتیبانی می‌شوند و خروجی نهایی قابل چاپ و بایگانی است.

⚙️ موتور گردش کار مشترک

مرخصی، مأموریت، فیش حقوقی و پشتیبانی داخلی همه روی یک موتور تأیید اجرا می‌شوند که مرحله‌ها را بر اساس نقش، دپارتمان، مدیر مستقیم یا شرط مبلغی تعیین می‌کند، مهلت پاسخ می‌گذارد و مرحله‌های غیرضروری را خودش رد می‌کند.

🌐 دوزبانگی واقعی

فارسی راست‌چین و English چپ‌چین با تعویض آنی — و مهم‌تر: جهت صفحه، تقویم، قالب اعداد و حتی خروجی‌های چاپی و PDF هم با زبان عوض می‌شوند.

🔐 دسترسی چندلایه با جداسازی داده

علاوه بر نقش‌های سازمانی، داده بر اساس دکل ایزوله می‌شود: کاربر هر دکل فقط داده‌ی همان دکل را می‌بیند و مدیر چند دکل، فقط دکل‌های تحت نظر خودش.

🎨 برندپذیری کامل

نام و لوگوی شرکت، رنگ‌های سامانه، صفحه‌ی ورود و سربرگ نامه‌ها همه از داخل پنل تنظیم می‌شوند. سامانه با هویت بصری هر سازمان بالا می‌آید، نه با یک ظاهر ثابت.

🤖 دستیار هوشمند

به زبان طبیعی به سؤال‌هایی مثل «چند دستور کار باز داریم؟» جواب می‌دهد. عمداً فقط می‌خواند — هیچ‌وقت چیزی ثبت یا ارسال نمی‌کند.

💾 بکاپ خودکار و بازیابی

بکاپ شبانه با تعداد نسخه‌ی قابل تنظیم، و بازیابی از داخل پنل بدون نیاز به دسترسی سرور. اعلان چندکاناله هم نمی‌گذارد کار پشت گردش تأیید معطل بماند.

📱 روی موبایل و دسکتاپ

علاوه بر مرورگر، به‌صورت اپلیکیشن روی موبایل نصب می‌شود و نسخه‌ی دسکتاپ مستقل هم دارد.

وقتی کاری عقب می‌افتد

وقتی تجهیزی خراب می‌شود

آخر روز — گزارش از خودِ کارها ساخته می‌شود

گزارش روزانه به تفکیک دپارتمان تولید می‌شود و در لحظه‌ی ثبت قفل می‌شود؛ با تغییر بعدی کارها عوض نمی‌شود، چون یک گزارش امضاشده نباید بازنویسی شود.

What Davam is

A web-based CMMS/PMS for any organisation that owns physical assets and has to keep them running. Nothing in its logic is tied to one industry — asset, maintenance plan, work order, failure and indicator mean the same thing wherever maintenance is done.

One honest note: the current build carries drilling vocabulary — the unit that separates assets is called a rig. Deploying into another industry means setting that label to whatever fits (“plant”, “site”, “line”); the underlying structure and logic do not change.

🌳 A precise asset register

Equipment is modelled as a deep hierarchy — from the rig down to the smallest replaceable part — and every item carries its own technical code, model and history. Existing structures are bulk-imported from Excel, so going live does not mean typing in thousands of records by hand.

📅 Automated preventive maintenance

Daily, weekly and monthly cycles are defined once on the Jalali calendar, and the system generates the next day's work orders every night by itself. Plans and checklists are importable and editable from a file.

⛔ Delay discipline

Overdue work cannot be closed without a recorded delay reason. It is the single control that stops a monthly report from becoming a meaningless wall of green — and the one managers actually rely on.

⚠️ Failure and downtime management

Failures are logged with start and end time and downtime is computed automatically. Parts consumed, the fix and the preventive action are retained — exactly the data that becomes reliability indicators with no human transcription.

📈 Reliability indicators

MTBF, MTTR and availability alongside downtime hours and assets involved, breakable down by rig, department and period up to a year. Fleet trend is plotted against defined bands so a decline is visible before it becomes critical.

📗 Professional Excel output

Available from any list. The maintenance checklist export lays each department out on its own sheet, marks the status of every line and carries the due date and delay reason — with a fully flexible period.

🧾 Advanced requisition with precise tracking

Every request is traceable from the moment it is raised until the goods arrive, and it is always clear whose desk it sits on. Routing is multi-stage and amount-aware: small purchases take a shorter path.

🔎 Purchasing bottleneck detection

The pipeline is presented as sequential stages that point directly at where work has actually stalled. Management does not have to go hunting for someone.

⚖️ Three-way matching

Order, goods receipt and invoice are reconciled against each other and mismatches are flagged automatically; open commitment converts into confirmed cost once approved.

🏬 Inventory with full movement history

Multi-warehouse stock, goods in transit and a per-item movement ledger. Repairable and warrantied items follow their own path, and parts consumption links straight back to the maintenance cost of the specific asset. Multi-currency control and per-rig petty cash are included.

📜 Full official correspondence

Letters are composed on official letterhead, numbered automatically, routed for approval and stamped with a scanned signature. Internal and external recipients, copies, attachments, confidentiality and urgency are supported, and the output is print- and archive-ready.

⚙️ One shared workflow engine

Leave, travel, payslips and internal support all run on a single approval engine that resolves stages by role, department, direct manager or amount threshold, applies deadlines, and skips unnecessary steps on its own.

🌐 Genuine bilingualism

Persian (RTL) and English (LTR) switch instantly — and crucially the page direction, calendar, number formatting and even printed and PDF output switch with the language.

🔐 Layered access with data isolation

Beyond organisational roles, data is isolated per rig: a rig's users see only that rig's data, and a multi-rig manager sees only the rigs they supervise.

🎨 Complete white-labelling

Company name and logos, system colours, the login screen and letterheads are all set from inside the panel. The system comes up wearing each organisation's identity, not a fixed skin.

🤖 Intelligent assistant

Answers natural-language questions such as “how many work orders are open?”. Deliberately read-only — it never files or sends anything.

💾 Automatic backup and restore

Nightly backups with configurable retention, and restore from inside the panel without server access. Multi-channel notifications keep work from stalling behind an approval.

📱 On mobile and desktop

Beyond the browser it installs as a mobile app, and a standalone desktop build is available.

A working day in Davam

The clearest explanation of Davam is to follow one real day.

The night before — the system builds tomorrow's work

Work orders are generated automatically from the PM schedules against the Jalali calendar. Nobody opens anything by hand.

Morning — everyone sees only their own work

A technician opens “My desk” and sees only their own tasks, on their own rig. The checklist opens inline, and every item takes one of: done, not required, not done, needs parts, escalated to management.

When work slips

Overdue work cannot be closed without a delay reason. That is the only thing keeping the overdue report honest instead of letting everything turn green.

When equipment fails

The failure is logged with start and end time; downtime is computed automatically, and the parts consumed, the fix and the preventive action are kept. Those are what later produce MTBF and MTTR.

End of day — the report builds itself from the work

The daily report is produced per department and frozen the moment it is filed; it does not change when tasks change afterwards, because a signed report must not rewrite itself.

Month end — handover

Reports are archived into Jalali year and month folders and can be handed over as a single ZIP or Excel file.

🔑 Access token: the release repository is private, so installation needs a read-only token, supplied with the install command. It is unrelated to the product licence — the licence governs use, the token only permits fetching the package. On the server it lives at /etc/davam/token with mode 600 owned by root, not in .env.

Installation

The whole install runs through the GitHub API — nothing is uploaded by hand.

Fetch the installer

Downloaded straight from the private repository with your token.

export DAVAM_GH_TOKEN='your-token-here'

curl -fsSL \
  -H "Authorization: Bearer $DAVAM_GH_TOKEN" \
  -H "Accept: application/vnd.github.raw" \
  https://api.github.com/repos/m0000hamad/davam/contents/davam.sh \
  -o davam.sh

Run the menu

Pick option 1 (Docker) or option 2 (bare-metal).

bash davam.sh

Done

The script installs prerequisites, pulls the latest release, generates a random database password and secret key, configures the firewall, runs an acceptance check, and prints the URL and login.

Updating

In all three routes the database, attachments and .env are preserved, and a backup is taken automatically before every update.

🖱 From inside the app

Settings → System update: the new version, its changelog, and one install button. Enable it once on the server:

bash davam.sh agent-install

📋 From the menu

bash davam.sh, then option 4 (latest) or 5 (specific version). The install method is detected automatically.

⌨️ From the command line

bash davam.sh check
bash davam.sh update
bash davam.sh update 6.31.0
bash davam.sh changes 6.30.0
Per-customer channels: each installation can follow its own channel — UPDATE_CHANNEL for customer-specific builds and UPDATE_PIN as a version ceiling, for customers who must stay on an approved release.
Why the API never touches the server itself: the backend only records a request; an agent on the host carries it out. If the API could reach Docker or systemd, any API compromise would become root access.

Security

Secure from minute zero

The database password and secret key are generated randomly per installation — no default value ever reaches production.

Layered access

JWT and bcrypt, admin/manager/user roles, and per-rig data isolation. Audit log for sensitive operations.

Small attack surface

The backend listens on an internal port only; external traffic goes through nginx. The repository token is read-only and single-repo.

HTTPS in one command

bash davam.sh ssl example.com — Let's Encrypt certificate with automatic renewal.
